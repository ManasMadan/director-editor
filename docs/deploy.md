# Deploying

How code gets from a merge to running clusters. The charts, environments and GitOps
layout are in [deploy/README.md](../deploy/README.md), the clusters (k3s on your own
machines) and their DNS in [infra/tofu/README.md](../infra/tofu/README.md), and the
GitHub settings the workflows need in [repository-settings.md](repository-settings.md).

The application, its Postgres (CloudNativePG, with continuous backups), Valkey, object
storage (RustFS), the mail server (Stalwart) and, where a cluster opts in, Jaeger and
Prometheus all run in the cluster. Cloudflare stays in front, and third-party APIs
(Gemini and YouTube, Google sign-in, Turnstile) stay external. Production runs on one
Compute Engine VM, an e2-standard-8 (8 vCPUs, 32 GB, about $210 a month; sizing in
[infra/tofu/README.md](../infra/tofu/README.md)). It also uses Google Cloud's own
services where they do the job better: media in Cloud Storage instead of RustFS, product
events in BigQuery, and indexing on a private Cloud Run service
([below](#the-cloud-run-indexer)).

## Images

`docker-bake.hcl` defines every image: `api`, `worker`, `notifications` and `webhooks`
(one Dockerfile, `deploy/docker/node-service.Dockerfile`), `web`, `ai` (also runs the AI
worker) and `migrate` (`prisma migrate deploy`). Images are `<REGISTRY>/<name>:<TAG>`,
with `RELEASE` (the commit SHA in CI) stamped in, so logs, errors and the web app report
which build is running.

```sh
docker buildx bake              # every image, for this machine
docker buildx bake api web      # some of them
```

Every image builds in a job of its own, in CI, in deploy.yml (once per architecture) and
for previews: seven images on one runner ran it out of disk. On every pull request CI's
**Container images** jobs build each image, fail on a fixable critical or high
vulnerability (Trivy), and start it against Postgres and Valkey to check it answers
(`scripts/image-smoke.ts`). A finding reviewed as not reaching the services (in a base-image
package nothing loads, while the base image's rebuild is pending) goes in
`.trivyignore.yaml` with the reason and an expiry, after which the scan fails again. The
ai image installs Debian's security updates at build time, since Python links the system
OpenSSL. Build caches are kept per image and architecture
(`<image>-<arch>`): deploy.yml writes them on master, and CI, previews and kind read them.
CI's run on a push to master writes the amd64 ones too, with the same build arguments, so
deploy.yml's amd64 build of that commit reuses every layer rather than building it again.

## Environments

| Environment | Where | Changes when |
|---|---|---|
| local | kind on your machine (`bun run k8s:up`, `k8s:smoke`, `k8s:down`) | you run it |
| preview | a namespace per labelled pull request, on the cluster that hosts previews | the pull request is pushed to |
| staging | its own cluster | every merge to `master` |
| production | its own cluster | a promotion pull request is merged |

Each has its values in `deploy/environments/<env>/` (`data.yaml`, `stack.yaml`) and its
Secrets there too, encrypted with SOPS in `secrets/` and decrypted by Argo CD (kind's are
generated by `k8s:up`). Argo CD installs the `data` release (Postgres, Valkey, RustFS)
before `stack`, and the stack's migration Job runs before its services on every sync.
Migrations are expand-then-contract ([database.md](database.md#expand-then-contract)), so
the previous release keeps working against the new schema during a rollout and after a
rollback.

## master → staging

`.github/workflows/deploy.yml`, after CI succeeds on a push to `master`:

1. builds every image for amd64 and arm64 and pushes them to
   `ghcr.io/manasmadan/director-editor/<image>:sha-<commit>`;
2. merges them into multi-arch tags, signs each with cosign and attaches build
   provenance to it, and an SBOM to each of its platform images (one per architecture,
   since an SBOM describes one platform's files); staging deploys only once every image
   has them. Production's image policy admits only images this workflow signed on
   `master`. Signing is keyless by default: production's admission then checks
   signatures against Sigstore's public transparency log (`rekor.sigstore.dev`), so an
   outage there stops new pods from starting. To depend on nothing public, sign with a
   key pair instead: `cosign generate-key-pair`, the private key and its password as the
   `COSIGN_PRIVATE_KEY` and `COSIGN_PASSWORD` secrets, the public key as
   `imagePolicy.publicKey` in `deploy/platform/config/values.yaml`;
3. commits the new tag to `deploy/environments/staging/stack.yaml` (as the repository's
   GitHub App, `[skip ci]`), and Argo CD rolls it out.

Every commit gets its own run, so every commit on master has images and can be
released, however quickly merges follow each other. Moving staging is one run at a
time, never backwards (a run that finishes after a newer commit's leaves staging where
it is), and its push retries on top of whatever landed on master meanwhile.

## Releases → production

Releases are version tags pushed by hand, on a commit of `master`:

```sh
git tag v1.4.0 && git push origin v1.4.0
bun run promote v1.4.0
```

Tag a commit that deployed: the merge once deploy.yml has passed for it, or the staging
bump deploy.yml commits right after (usually master's head; it has no images of its own,
so a release of it ships its parent's, which is the same code). The tag starts
`.github/workflows/release.yml`, which checks it: a version, on master, with images
(waiting while CI and deploy.yml still run on the commit). It then publishes the GitHub
release with notes grouped from the Conventional Commit titles since the previous tag
(`scripts/release.ts`). Choose the number from the notes
(`bun scripts/release.ts notes HEAD` shows what's unreleased): a breaking change (`!`) is
a new major version, a `feat` a minor one.

`bun run promote` opens the promotion pull request (`release/production-v<version>`),
from your own GitHub login so CI runs on it: it writes
`deploy/environments/production/release.yaml`, the revision production is deployed from
(the tag, so its charts, values, Secrets and add-ons are the release's) and the release's
images (the same rule as the check), the ones already running on staging. It refuses
when there are none. Merging the promotion is the deploy; a chart change merged to
master reaches production only this way (deploy/README.md, "GitOps").

## Rollback

Argo CD syncs automatically and self-heals, so a change made in the cluster is undone;
roll back in git:

- **Production**: promote the previous release again (`bun run promote v<previous>`),
  which puts back its charts and values as well as its images, or revert the promotion
  commit on `master` (through a pull request). Either pull request changes only
  `deploy/environments/production/release.yaml`, so CI runs only lint, the charts and
  the scripts' tests on it, a few minutes rather than the whole pipeline, and the
  previous release's images are already built and signed. Merging it is the rollback.
- **Staging**: revert the bump commit, or let the next merge replace it.

The database isn't rolled back: the previous release already works with the current
schema. If a migration itself is wrong, fix forward with a new one.

## The Cloud Run indexer

Production's ai worker can send each plan job's short to a private Cloud Run service,
`director-indexer`, so Gemini's long video calls and the audio download (yt-dlp, then
`gs://director-media-…/audio/<videoId>.m4a`) run off the VM. It's the same `ai` image
with another entrypoint (`uvicorn app.indexer:app`, apps/ai/app/indexer.py) and the same
code the worker runs without it (apps/ai/app/indexing.py). It has no database: it
answers with the plan, the audio's key and what the run used, and the worker stores and
counts them.

Only the VM's account may call it: Cloud Run lets in only the service's invokers
(`--no-allow-unauthenticated`), and the indexer checks the ID token again (audience
`INDEXER_URL`, email `INDEXER_INVOKER`). It calls Vertex AI and Cloud Storage as its own
account, `director-indexer@…`, through Application Default Credentials: no express key
or key file. Production's ai worker sets `INDEXER_URL` to it
(`deploy/environments/production/stack.yaml`); without it, plans are indexed in the
worker itself, the same way.

It isn't deployed by Argo CD; run these by hand (or from a release checklist) with
`gcloud` signed in as a project owner, on every release: it answers with the release it
runs (`RELEASE`), and a worker on another release logs "the Cloud Run indexer runs
another release", stops using it and writes plans itself until it's deployed again. An
indexer left on an older release otherwise writes plans the way that release did (one
from before assets writes plans without asset slots). The variables, once per shell:

```sh
PROJECT=project-18e15b18-c92e-44bb-9bf
REGION=us-central1
BUCKET=director-media-1053522546520
COMMIT=<the commit production runs>          # release.yaml's ai image is sha-<commit>
SOURCE=ghcr.io/manasmadan/director-editor/ai:sha-$COMMIT
IMAGE=$REGION-docker.pkg.dev/$PROJECT/director/ai:sha-$COMMIT
INDEXER=director-indexer@$PROJECT.iam.gserviceaccount.com
VM=director-vm@$PROJECT.iam.gserviceaccount.com
# Cloud Run's deterministic URL: https://<service>-<project number>.<region>.run.app
INDEXER_URL=https://director-indexer-1053522546520.$REGION.run.app
```

Once per project (skip what exists):

```sh
gcloud services enable run.googleapis.com artifactregistry.googleapis.com --project=$PROJECT
gcloud artifacts repositories create director --repository-format=docker \
  --location=$REGION --project=$PROJECT
gcloud iam service-accounts create director-indexer --project=$PROJECT \
  --display-name="Director indexer (Cloud Run)"
# Gemini on Vertex AI, and the audio it captures into the media bucket.
gcloud projects add-iam-policy-binding $PROJECT --member=serviceAccount:$INDEXER \
  --role=roles/aiplatform.user
gcloud storage buckets add-iam-policy-binding gs://$BUCKET \
  --member=serviceAccount:$INDEXER --role=roles/storage.objectAdmin
```

Each release (Cloud Run pulls from Artifact Registry, not GHCR, so the image is copied
first; `crane copy $SOURCE $IMAGE` does the same):

```sh
gcloud auth configure-docker $REGION-docker.pkg.dev
docker buildx imagetools create --tag $IMAGE $SOURCE

gcloud run deploy director-indexer --project=$PROJECT --region=$REGION \
  --image=$IMAGE \
  --command=uvicorn --args=app.indexer:app,--host,0.0.0.0,--port,8080 --port=8080 \
  --service-account=$INDEXER --no-allow-unauthenticated \
  --timeout=900 --memory=2Gi --cpu=1 \
  --set-env-vars=NODE_ENV=production,LOG_LEVEL=info,RELEASE=sha-$COMMIT,INDEXER_URL=$INDEXER_URL,INDEXER_INVOKER=$VM,GOOGLE_VERTEX=true,GOOGLE_CLOUD_PROJECT=$PROJECT,VERTEX_LOCATION=global,INDEX_MODEL=gemini-4-argon,INDEX_FALLBACK_MODEL=gemini-3.1-pro-preview,MEDIA_BUCKET=$BUCKET

# The VM's account (the ai worker) may call it.
gcloud run services add-iam-policy-binding director-indexer --project=$PROJECT \
  --region=$REGION --member=serviceAccount:$VM --role=roles/run.invoker
```

`--timeout=900` is the worker's own (`INDEX_REQUEST_SECONDS` in app/indexing.py): every
retry and the fallback model of a slow short fit in it. `INDEX_MODEL` and
`INDEX_FALLBACK_MODEL` should match the worker's (the worker records usage under its own
`INDEX_MODEL`). Check the service's URLs include `$INDEXER_URL`:

```sh
gcloud run services describe director-indexer --project=$PROJECT --region=$REGION \
  --format='value(metadata.annotations."run.googleapis.com/urls")'
```

Then check it from the VM, as its account:

```sh
TOKEN=$(curl -s -H 'Metadata-Flavor: Google' \
  "http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/identity?audience=$INDEXER_URL&format=full")
curl -s -H "Authorization: Bearer $TOKEN" $INDEXER_URL/health/live    # {"status":"ok"}
```

Finally point the worker at it: set `INDEXER_URL: <$INDEXER_URL>` in the ai worker's
`env` in `deploy/environments/production/stack.yaml` (where its comment says), and
promote. Unsetting it again is the rollback: the worker goes back to indexing itself.

## The Cloud Run clipper

Director's continuous recording cuts each attempt a member makes at a shot out of the
session's footage into a take of its own: the worker sends the attempt (presigned reads
of its slices, Director's marks, the part's pauses) to the AI service's
`/v1/director/clips`, which joins the slices, snaps the marks to the first and last words
with ffmpeg's silencedetect and re-encodes the stretch as an H.264 MP4. In production
that work runs on a private Cloud Run service, `director-clipper`, never in the ai pod:
the slices are whatever bytes a member uploaded, and ffmpeg decoding them belongs in a
container that holds no secrets or data, not in the pod with the database URL and the
service's keys (the ai service refuses to start in production without `CLIPPER_URL`).
It also keeps minutes of decoding off the VM, and its memory out of the ai pod's 768 MiB.
It's the same `ai` image (ffmpeg is in it) with another entrypoint
(`uvicorn app.clipper:app`, apps/ai/app/clipper.py) and the same code the ai service
runs in development (apps/ai/app/clipping.py). It has no database, Redis, storage or
Vertex AI access: the footage comes and goes by presigned reads the worker signs, and the
take goes back in the response.

Wherever it runs, ffmpeg reads the footage defensively (apps/ai/app/clipping.py): the
first bytes must be the part's declared type's (apps/api checks the first slice too), the
demuxer is pinned to that type (`-f matroska` or `-f mov`) instead of guessed from the
content, it may open local files only (`-protocol_whitelist file`), it gets two threads,
and it runs through apps/ai/app/jail.py: an environment of `PATH` alone, ten minutes of
CPU, files of at most 64 MiB, no core dumps and, on Linux, 2 GiB of address space. The
ai service's own wall-clock limit is five minutes per ffmpeg run, and it cuts one attempt
at a time.

Only the VM's account may call it (`--no-allow-unauthenticated`, and the clipper checks
the ID token again: audience `CLIPPER_URL`, email `CLIPPER_INVOKER`). Its own account,
`director-clipper@…`, needs no roles at all: give it none.

Like the indexer, it isn't deployed by Argo CD. With the variables from "The Cloud Run
indexer" above, and these:

```sh
CLIPPER=director-clipper@$PROJECT.iam.gserviceaccount.com
CLIPPER_URL=https://director-clipper-1053522546520.$REGION.run.app
```

Once per project:

```sh
gcloud iam service-accounts create director-clipper --project=$PROJECT \
  --display-name="Director clipper (Cloud Run)"
```

Each release (the image copied to Artifact Registry as for the indexer):

```sh
gcloud run deploy director-clipper --project=$PROJECT --region=$REGION \
  --image=$IMAGE \
  --command=uvicorn --args=app.clipper:app,--host,0.0.0.0,--port,8080 --port=8080 \
  --service-account=$CLIPPER --no-allow-unauthenticated \
  --timeout=900 --memory=4Gi --cpu=2 --concurrency=1 --max-instances=4 \
  --set-env-vars=NODE_ENV=production,LOG_LEVEL=info,CLIPPER_URL=$CLIPPER_URL,CLIPPER_INVOKER=$VM

# The VM's account (the ai service) may call it.
gcloud run services add-iam-policy-binding director-clipper --project=$PROJECT \
  --region=$REGION --member=serviceAccount:$VM --role=roles/run.invoker
```

`--timeout=900` is what the ai service waits for it (`CLIP_REQUEST_SECONDS` in
app/clipping.py): a whole part's download and both ffmpeg runs (five minutes each at
most) fit in it; the worker waits a minute longer for the ai service. One attempt per
instance (`--concurrency=1`): each is a whole ffmpeg run, and Cloud Run adds instances
for the next, up to `--max-instances`. `--memory=4Gi` because Cloud Run's `/tmp` is in
memory: a part's footage (at most 1.2 GB, 150 slices of 8 MB) is written there, next to
ffmpeg's 2 GiB. Check it from the VM as for the indexer (`$CLIPPER_URL/health/live`).

Production's `CLIPPER_URL` is already in the ai and ai-worker services' `env` in
`deploy/environments/production/stack.yaml`, so deploy the clipper before the release
that carries recording: until it answers, every attempt waits and retries, then fails
(UPSTREAM_UNAVAILABLE), and nothing is cut in the ai pod instead. A failing clipper is
rolled back on Cloud Run (`gcloud run services update-traffic director-clipper
--to-revisions=<previous>=100`), never by unsetting `CLIPPER_URL`, which production
refuses.

The worker reaches the ai service with the api's call-signing secret
(`AI_SERVICE_SECRET`, taken from the ai Secret by the stack chart's `secretKeys`) and
`AI_URL`; the ai service's network policy lets the worker in.

Raw footage lives in the media bucket under `recordings/`, deleted by the worker's
`recording-retention` task when its session expires. The bucket needs a lifecycle rule
on that prefix as a backstop, and it isn't applied yet: apply it before the release that
carries recording. Without it, nothing outlives the longest keeping (14 days) only while
the worker's task runs, and a slice PUT through a still-valid upload URL (ten minutes)
after its session was deleted is never deleted at all:

```sh
cat > /tmp/lifecycle.json <<'EOF'
{"rule": [
  {"action": {"type": "Delete"}, "condition": {"age": 90, "matchesPrefix": ["director/speech/"]}},
  {"action": {"type": "Delete"}, "condition": {"age": 15, "matchesPrefix": ["recordings/"]}}
]}
EOF
gcloud storage buckets update gs://$BUCKET --lifecycle-file=/tmp/lifecycle.json
gcloud storage buckets describe gs://$BUCKET --format='value(lifecycle)'
```

(A lifecycle file replaces the bucket's rules: it carries the spoken lines' 90-day rule,
docs/files.md, too.)

## The Cloud Run aligner

The editor lines up each match cut (the anchor, a wrist with a watch, kept on the same
spot while the background changes between two shots) through the AI service's
`/v1/director/match-cuts`: ffmpeg reads the half second either side of the cut from both
takes (presigned reads apps/api signs), Gemini (`DIRECTOR_MODEL`) boxes the anchor in the
two boundary frames, and OpenCV refines it (template matching, then ECC on the anchor's
patch) into where to cut and how to move the incoming take. With `ALIGNER_URL` set on the
ai service, that runs on a private Cloud Run service, `director-aligner`, instead of in
the ai pod: decoding two takes and the OpenCV work are CPU the VM's other services need.
It's the same `ai` image (ffmpeg, OpenCV and NumPy are in it) with another entrypoint
(`uvicorn app.aligner:app`, apps/ai/app/aligner.py) and the same code the ai service runs
without it (apps/ai/app/aligning.py). It has no database, Redis or storage access: the
takes come by presigned reads, and the answer carries what the Gemini call used, which
the ai service counts against the workspace's tokens (`DIRECTOR_TOKENS_PER_ALIGNMENT` is
the most one cut may reserve).

Only the VM's account may call it (`--no-allow-unauthenticated`, and the aligner checks
the ID token again: audience `ALIGNER_URL`, email `ALIGNER_INVOKER`). It calls Vertex AI
as its own account, `director-aligner@…`. Until `ALIGNER_URL` is set on the ai service,
match cuts are lined up in the ai pod itself, the same way.

Like the indexer, it isn't deployed by Argo CD. With the variables from "The Cloud Run
indexer" above, and these:

```sh
ALIGNER=director-aligner@$PROJECT.iam.gserviceaccount.com
ALIGNER_URL=https://director-aligner-1053522546520.$REGION.run.app
```

Once per project:

```sh
gcloud iam service-accounts create director-aligner --project=$PROJECT \
  --display-name="Director aligner (Cloud Run)"
gcloud projects add-iam-policy-binding $PROJECT --member=serviceAccount:$ALIGNER \
  --role=roles/aiplatform.user
```

Each release (the image copied to Artifact Registry as for the indexer):

```sh
gcloud run deploy director-aligner --project=$PROJECT --region=$REGION \
  --image=$IMAGE \
  --command=uvicorn --args=app.aligner:app,--host,0.0.0.0,--port,8080 --port=8080 \
  --service-account=$ALIGNER --no-allow-unauthenticated \
  --timeout=60 --memory=1Gi --cpu=2 --concurrency=2 \
  --set-env-vars=NODE_ENV=production,LOG_LEVEL=info,RELEASE=sha-$COMMIT,ALIGNER_URL=$ALIGNER_URL,ALIGNER_INVOKER=$VM,GOOGLE_VERTEX=true,GOOGLE_CLOUD_PROJECT=$PROJECT,VERTEX_LOCATION=global,DIRECTOR_MODEL=gemini-3.8-flash

# The VM's account (the ai service) may call it.
gcloud run services add-iam-policy-binding director-aligner --project=$PROJECT \
  --region=$REGION --member=serviceAccount:$VM --role=roles/run.invoker
```

`DIRECTOR_MODEL` should match the ai service's (it records the usage under its own).
The ai service waits 27 seconds for it (`ALIGN_REQUEST_SECONDS` in app/aligning.py),
under apps/api's 30-second wait for the ai service, so `--timeout=60` is plenty. Check it
from the VM as for the indexer (`$ALIGNER_URL/health/live`), then set
`ALIGNER_URL: <$ALIGNER_URL>` in the ai service's `env` in
`deploy/environments/production/stack.yaml` and promote. Unsetting it again is the
rollback: the ai pod lines up match cuts itself.

## Previews

Adding the `preview` label to a pull request from this repository (not a fork) runs
`.github/workflows/preview.yml`: it builds the head commit's images (amd64) as
`sha-<commit>`. Argo CD's previews ApplicationSet deploys it, at
`https://pr-<number>.preview.<domain>` (the domain of the cluster hosting previews, from
OpenTofu), and once it's running Argo CD's notifications post that address on the pull
request through the GitHub App (`argocd-notifications-secret`, deploy/README.md). It runs
in its own namespace with its own database and Valkey, and the Secrets every preview shares
(`deploy/environments/preview/secrets/`). A preview's mail never leaves it: it goes to a
Mailpit in its namespace (`kubectl -n pr-<number> port-forward svc/mailpit 8025`), so a
pull request's code can't mail real people or spend the domain's reputation. Argo CD
notices a new head commit before its
images are pushed, so the first sync fails and retries with backoff for about half an
hour until they are. New pushes rebuild; removing the label or closing the pull request
deletes it, and closing it deletes its images from GHCR too (every `sha-<commit>` of the
pull request's commits).

A preview runs the pull request's images with the charts, values and Secrets of the
branch it targets, never the pull request's own: a fork's charts could otherwise run any
image with those Secrets once someone added the label. So changes to `deploy/` show up
in staging after merging, not in the preview. The preview Secrets are encrypted to a key
of their own, which the cluster decrypts previews with alone, so a staging Secret copied
into that directory doesn't decrypt there (and `charts:check` refuses it).

## Infrastructure

Each environment is k3s on machines you run, with Cloudflare in front, from one
OpenTofu root (`infra/tofu/envs/k3s`) applied per environment.
`.github/workflows/infra.yml` posts a `tofu plan` on pull requests that change
`infra/tofu`, for each environment in the `TOFU_TARGETS` repository variable. Applying is
a manual run (environment, apply), gated by the GitHub environment's reviewers; it
installs or upgrades k3s over SSH, updates the DNS records and bootstraps Argo CD. A
pull request's plan runs in an environment of its own that has no SSH key and no age
keys (a plan needs neither) and read-only credentials otherwise, and waits for a
reviewer, since it still decrypts the state (docs/repository-settings.md).

`kind.yml` deploys the whole stack to kind when images, charts or migrations change, and
nightly: every image, the data chart (its credentials generated, RustFS's bucket
created), the stack, the routes smoke-tested through the gateway (the site's and the
files host's), and re-encryption run the way operators run it.

## What's GitHub-only

Most of the logic is in `bun` scripts (`scripts/release.ts`, `scripts/charts.ts`,
`scripts/e2e.ts`, …) that any CI can run, and the workflows' YAML mostly runs on
Forgejo or Gitea Actions as it is. These parts are GitHub's own, and each has a
replacement on another host:

| On GitHub | What it does here | Elsewhere |
|---|---|---|
| `workflow_run` | deploy.yml after CI passes | GitLab: one pipeline with stages; Forgejo: call the deploy steps at the end of CI's workflow on `push` to master |
| `merge_group` | CI on the merge queue | GitLab merge trains; Forgejo has none (merge after CI on the branch) |
| environments with reviewers | infra.yml's plan and apply, staging's bump | GitLab protected environments; Forgejo: a manual job on a protected branch |
| OIDC keyless signing (`id-token: write`) | cosign signatures production admits | a key pair (`COSIGN_PRIVATE_KEY`, `imagePolicy.publicKey`), which any CI can use |
| `attest-build-provenance`, `attest-sbom` | provenance and SBOM attached to the images | `cosign attest` with the same key |
| CodeQL, code scanning, dependency review | security.yml's checks and the ruleset's gate | Semgrep, Trivy and OSV-Scanner run as failing jobs |
| GHCR (`ghcr.io`) | the image registry | Harbor, Zot, Forgejo's or GitLab's registry |
| the GitHub App (`create-github-app-token`) | the staging bump past the ruleset, Renovate | a bot account's token |
| `claude-code-action` | the optional Claude review of pull requests (claude-review.yml) | `claude -p` with the same prompt, `--permission-mode dontAsk` and tool list in any CI job |
| `gh` in `scripts/release.ts` | a release's CI runs, opening the promotion pull request | `tea` (Forgejo) or `glab` (GitLab) |
| Argo CD's `pullRequest.github` generator | one preview per labelled pull request | its `gitea` and `gitlab` generators |
