# Database

One Postgres 18 database (with pgvector and pg_trgm), split into schemas by owning
service. The Prisma schema is in `packages/db/prisma/schema/`, one file per schema;
migrations in `packages/db/prisma/migrations/`. Prisma owns all DDL, including the
Python service's tables.

## Schemas and owners

Each schema has one service that writes it. Other services get only what their job
needs, granted in migrations (often column by column).

| Schema | Owner | Also used by |
|---|---|---|
| `auth` | api (better-auth: users, sessions, organizations, API keys, OAuth) | notifications reads user identity and membership columns; worker purges expired rows through `auth.purge_expired()`; ai calls `auth.mcp_grant_active` |
| `app` | api (product data: todos, its outbox) | worker reads the outbox and stamps `published_at` |
| `audit` | worker (append-only, partitioned by month) | api reads its organization's rows |
| `webhooks` | webhooks (deliveries, inbound events, its outbox) | api edits `endpoint`; worker relays the outbox |
| `notifications` | notifications (inbox, delivery log, digests, suppressions) | api edits preferences, settings, devices and read state |
| `files` | api (uploads) | worker writes the processing columns |
| `billing` | api (mirror of Stripe) | |
| `ai` | ai (documents, chunks, token usage) | |

Conventions for every model (`base.prisma`): `uuidv7()` ids generated by Postgres,
`timestamptz(3)` timestamps, snake_case columns and tables through `@map`/`@@map`, and
`@@schema` on every model.

## Roles

Created outside migrations: `infra/postgres/init/01-roles-and-databases.sql` locally and
in CI, the CloudNativePG cluster's bootstrap and managed roles in Kubernetes
(`deploy/charts/data`, which also generates each role's password in the cluster). Local
passwords equal the role names.

| Role | Used by | Notes |
|---|---|---|
| `migrator` | `prisma migrate`, test setup | Owns every schema and table. `NOBYPASSRLS`. |
| `app_api`, `app_worker`, `app_notifications`, `app_webhooks`, `app_ai` | one service each | `NOBYPASSRLS NOINHERIT`, only the grants in migrations. |
| `app_readonly` | Claude Code's Postgres MCP server, **local database only** (`02-readonly-role.sql`, reapplied by `bun run db:up`) | `BYPASSRLS`, read-only transactions, `SELECT` on everything the migrator owns. Never in CI or a cluster. |

Extensions need a superuser, so the bootstrap script creates them, not migrations.
Because the services run with production's privileges locally and in tests, a missing
grant fails there first.

When a service needs something outside its grants (creating audit partitions, purging
another schema's history, registering a device), a migration adds a narrow
`SECURITY DEFINER` function and grants `EXECUTE` on it (see the
`audit_log_and_retention` and `push_devices` migrations). Forced row-level security
applies to the function's owner too, so every table it reads or writes under FORCE needs
an `owner_functions` policy for `migrator`, or it silently sees no rows; the database's
security tests fail on any that lacks one.

Prisma's errors that mean something to a client become catalog errors wherever they
surface (`fromPrismaError` in `packages/nest-common`, applied to procedures and to the
HTTP error filter): a unique constraint lost to a concurrent write or a write conflict is
`CONFLICT`, a row gone between reading and writing is `NOT_FOUND`, and a pool or
transaction timeout is `SERVICE_UNAVAILABLE`. Anything else stays `INTERNAL`. A call that
means something more specific (`PHONE_NUMBER_TAKEN`) still catches its own.

## Row-level security

Tenant tables have `ENABLE` and `FORCE ROW LEVEL SECURITY` (FORCE applies the policy to
the table owner too) and a policy on a transaction-local setting:

- **Organization data** (`app.todo`, `webhooks.endpoint`/`delivery`,
  `billing.customer`/`subscription`, `ai.*`, reads of `audit.audit_log`):
  `org_id = nullif(current_setting('app.org_id', true), '')::uuid`.
- **Per-user data** (`notifications.notification`/`preference`/`settings`/`device`/`digest_item`,
  `files.file`): the same on `user_id` and `app.user_id`.

`billing.trial_card` has neither: the one-trial-per-card check has to see every
workspace's cards, and a row holds only Stripe's ids (a card fingerprint and a
subscription), no workspace's data.

`nullif` keeps the policy valid when the setting is unset: it resets to `''`, and
`''::uuid` would raise instead of matching nothing. A query without the setting sees no
rows.

The helpers in `packages/db/src/tenancy.ts` set it:

```ts
const db = withTenant(database.read, orgId);        // each query: set_config + query, one batch
await db.todo.findMany();

await tenantTx(database.write, orgId, async (tx) => {  // one interactive transaction
  await tx.todo.update(...);
  await emitEvent(tx, "todo.completed.v1", todo.id, payload);
});
```

`withUser` / `userTx` are the same for `app.user_id`. They take a branded id, an `OrgId`
or a `UserId` from `@repo/contracts/ids` ([architecture.md](architecture.md#auth-and-tenancy)),
so a user's id can't scope a workspace's query. The setting must be applied inside
the transaction that runs the query, because PgBouncer (transaction mode) hands each
transaction a different connection. `tenantTx` holds a connection until it ends, so it
contains database calls only: never await HTTP, Redis or a queue inside it. Nested
`$transaction` on a `withTenant` client throws.

In the API, `context.orgId` comes from the `inOrg` procedure (the session's active
organization, membership re-checked, or an API key's workspace). The Python service
has only `tenant(org_id)` in `apps/ai/app/db/session.py`; there is no unscoped session.

## Connections

`createDatabase({ url, poolMax, service })` (`packages/db/src/client.ts`) returns
`read` and `write` clients. They are the same primary today; repositories pick one per
query so read replicas are a change in that file only. Every connection is labelled
with the service (`application_name`) and has a 15 s statement timeout and a 10 s
idle-in-transaction timeout.

`Tx` is a branded transaction client: only `tenantTx`, `userTx` and `transaction`
produce one, so APIs that must run in a transaction (`emitEvent`) can't be called
without one.

## Changing the schema

1. Edit the owning schema's file in `packages/db/prisma/schema/`.
2. `bun run db:migrate`. Prisma asks for a name, writes
   `prisma/migrations/<timestamp>_<name>/migration.sql` from the diff (using
   `SHADOW_DATABASE_URL`) and applies it.
3. A new tenant table gets its `ENABLE`/`FORCE ROW LEVEL SECURITY`, policy and grants in
   the same migration. Prisma can't express those, nor functions or HNSW indexes, so
   they're hand-written SQL in it. Change a migration only before it ships; once it's on
   `master`, write a new one.
4. `bun run gen` if you didn't already (the Prisma client), and for `ai` tables, update
   `apps/ai/app/db/models.py`: `tests/test_models_match_db.py` fails when the SQLAlchemy
   models and the migrated database differ.

Other commands: `bun run db:deploy` applies pending migrations (setup and CI use it; the
`migrate` image runs `prisma migrate deploy` as a pre-install/pre-upgrade hook in
Kubernetes), `bun run db:reset` drops and re-applies everything locally, `bun run
db:studio` opens Prisma Studio.

### Expand, then contract

Migrations deploy before the code that uses them, and the previous release keeps
running during a rollout (and after a rollback), so every migration must work with both
versions:

1. Add the new column or table (nullable, or with a default).
2. Backfill.
3. Ship the code that uses it.
4. Drop the old one in a later release.

`bun run db:lint` runs Squawk (`.squawk.toml`) on the migrations added or changed since
`master` (or `$GITHUB_BASE_REF` in a pull request), and CI's **Migration safety** job
runs it on every change. It flags operations that take locks or rewrite tables while the
old release is serving. A flagged statement that is safe in context gets
`-- squawk-ignore <rule>` above it, with the reason. Long backfills are fine; set
`lock_timeout` so a migration can't block live traffic.

### Drift

CI's integration job runs `packages/db/scripts/drift.ts` (`bun run --cwd packages/db
drift`), which fails when the migrations, the Prisma schema and the migrated database
disagree. Differences Prisma can't model are listed in its `IGNORED` with the reason
(today, the pgvector HNSW index).

## Test databases

`packages/db/src/testing` gives each integration test file its own database, cloned
from a migrated template in milliseconds:

- `prepareTemplate()` runs once per test run (each package's vitest `globalSetup`). It
  applies migrations to `app_test` under an advisory lock, so parallel packages take
  turns. If a migration recorded in the template no longer matches its file, it rebuilds
  the template's schemas first. It also drops test databases left by runs that died
  (their name carries the owning pid).
- `createTestDatabase()` clones `app_test` into `app_test_<pid>_<random>` and grants
  `CONNECT` to the service roles. `testDb.urlFor("app_api")` connects as a service role,
  so grants and policies apply exactly as in production. `testDb.drop()` removes it.

`factories(db)` (from `@repo/db/testing`) writes test data directly as a service role:
`user`, `organization`, `member`, `userWithWorkspace`, `todo`. They skip side effects
(emails, audit, outbox); drive the API when those are what's tested.

The Python integration tests use the migrated `app` database directly (see
`apps/ai/tests/support.py`).

## Restore drill

`bun run db:restore-drill` (`scripts/restore-drill.ts`) proves a logical backup restores
(the clusters' own backups are Barman base backups and WAL: deploy/README.md, "Backups
and restore", says how to try those in staging): it dumps the database with `pg_dump`
(custom format), restores it into a scratch database
and requires an identical fingerprint: each table's row count and content hash,
row-level security flags and policies, grants, default privileges, functions, triggers,
extensions and sequence positions. The scratch database and dump are removed either
way.

```sh
bun run db:restore-drill                      # the local "app" database (compose postgres)
bun run db:restore-drill <database>           # another database
PG_CONTAINER=<name> bun run db:restore-drill  # Postgres in another container
```

Everything runs inside the Postgres container as its superuser. Roles and
database-level grants are cluster-wide and not in a dump: a restore into a new cluster
creates them first. CI runs the drill after the end-to-end suite, on the data it left.

## Backups and point-in-time recovery

In Kubernetes, CloudNativePG's Barman Cloud plugin backs up every environment that turns
`postgres.backups.enabled` on (staging and production): WAL is archived as it's written
and a base backup taken every day (the first right away), to a RustFS server of its own
in the cluster that only Postgres can reach. They're kept for
`postgres.backups.retention` (30 days in production), and any moment in that window can
be restored.

These are physical backups of the whole cluster, so unlike the drill's dump they carry
the roles, database grants and extensions too. Restoring is bootstrapping a new cluster
from them, optionally up to a point in time (`postgres.restore` in the environment's
`data.yaml`); CloudNativePG then sets the roles' passwords from the namespace's Secrets,
so the services connect as before. The procedure is in
[deploy/README.md](../deploy/README.md#backups-and-restore).
